# PSPL Expense Voucher Management System

A straightforward expense voucher workflow for Prachay Securities Private Limited. The app uses React and Vite, an Express API, and PostgreSQL.

## Stack and prerequisites

- Node.js and npm
- PostgreSQL
- React, Vite, Express, `pg`, `bcryptjs`, `jsonwebtoken`, and Multer

## Install and configure

```sh
npm install --prefix client
npm install --prefix server
```

Create a new development database using your PostgreSQL administrator, for example in `psql` or pgAdmin:

```sql
CREATE DATABASE pspl_expense_vouchers;
```

This creates a new database; it does not require modifying other databases. Copy `server/.env.example` to `server/.env`, then set your PostgreSQL values and a long, private `JWT_SECRET`. You can use either `DATABASE_URL` or `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, and `PGPASSWORD`. No real credentials belong in this repository.

Run the versioned migrations:

```sh
npm run migrate
```

Migration `002_voucher_workflow.sql` adds the voucher department, title, voucher date, employee signature snapshot, Director signature path, and list indexes. It does not drop tables or data.

## Development accounts

In `server/.env`, set all the `SEED_EMPLOYEE_*`, `SEED_DIRECTOR_*`, and `SEED_ACCOUNTS_*` values to local development names, emails, and passwords (minimum eight characters). Then run:

```sh
npm --prefix server run seed
```

Passwords are bcrypt-hashed before insertion. Existing emails are left unchanged, including their password. The seed is a local script; no public registration or seed endpoint exists. Never commit `server/.env`.

## Start the app

Run each command in its own terminal:

```sh
npm run dev:server
npm run dev:client
```

Vite serves the frontend and proxies `/api` to the Express server (port `3000` by default, configurable with `PORT`). Build the frontend with:

```sh
npm run build:client
```

## Roles and workflow

- **Employee:** create and save drafts, list and view only their own vouchers, edit/delete only drafts, upload a signature, and submit signed drafts. Submitted vouchers are read-only. Rejection reasons appear in voucher details.
- **Director:** view organization vouchers and pending approvals, upload a Director signature, and approve or reject pending vouchers. Approval requires the signature; rejection requires a reason. Decision transactions lock the voucher to prevent conflicting decisions. Directors cannot edit expense details.
- **Accounts:** view and filter organization vouchers, signatures, and approval information. Accounts has no write, approval, or rejection APIs.

Voucher numbers are generated by PostgreSQL identity and protected by a unique constraint. Amounts must be positive. Employee identity comes from the JWT, not request data. List filters and sort choices are validated and SQL values are parameterized; employee queries include an owner condition.

## Main API endpoints

- `POST /api/auth/login`, `GET /api/auth/me`
- `GET /api/vouchers/dashboard`, `GET /api/vouchers`
- `POST /api/vouchers`, `GET /api/vouchers/:id`, `PUT /api/vouchers/:id`, `DELETE /api/vouchers/:id`
- `POST /api/vouchers/:id/submit`
- `POST /api/vouchers/:id/decision` (Director only; JSON decision is `approved` or `rejected`)
- `POST /api/vouchers/signature` (Employee image; multipart field `signature`)
- `POST /api/vouchers/director-signature` (Director image; multipart field `signature`)
- `GET /api/vouchers/signatures/:filename` (authenticated and ownership-checked)
- `GET /api/health`, `GET /api/health/db`

Voucher filters include `search`, `status`, `department`, `category`, `employee`, `dateFrom`, `dateTo`, `amountMin`, `amountMax`, and `sort` (`newest`, `oldest`, `highest`, or `lowest`). Employee results remain restricted to the logged-in employee.

## Signatures and deployment limits

Images are restricted to PNG, JPEG, or WebP, checked against their file signature, and limited to 5 MB. Filenames are generated by the server; PostgreSQL stores paths, not image bytes. Development files live in `server/uploads/` and are excluded from Git. This local folder is not durable/shared storage for a multi-instance deployment; deployment should use persistent storage or an object store and a coordinated backup strategy. Signature downloads go through an authenticated API rather than a public static directory.

The frontend stores its JWT in `localStorage` to keep the session across reloads. JavaScript on the page can read it, so an XSS vulnerability could expose the token. It is not placed in URLs or logs; logout removes it from browser storage. Backend authorization is still enforced independently of frontend navigation.

## Tests and checks

```sh
npm --prefix server test
npm run build:client
```

Database-backed behavior also requires a running PostgreSQL server with the migrations applied and development accounts seeded. `GET /api/health/db` checks the connection.
